# 设计决策记录（ADR）

格式：背景 → 决定 → 为什么这么选 → 付出了什么代价 → 什么时候该推翻它。

---

## ADR-001 规则优先，LLM 是增强项而不是依赖项

**背景。** 巡检要挂 cron 无人值守跑。第一版直接把规划交给模型，结果是没 Key 就整条链路瘫掉，
而且评测集无法复现——模型温度调到 0 也不保证同一输入同一计划（服务端会换路由/版本）。

**决定。** 规划器与综合器各有规则、LLM 两条实现，**规则是默认与兜底**，LLM 只在
`LLM_API_KEY` 存在时介入，且它的输出必须经过逐条校验（未知工具丢弃、超预算截断、
依赖索引重映射）；校验不通过就回落到规则并把 `fallback_reason` 写进轨迹。

**代价。** 规则模板要覆盖 7 类意图，写起来比"一个 prompt 搞定"累得多，且新领域得补模板。

**什么时候推翻。** 如果评测显示 LLM 规划的意图准确率稳定高于规则 ≥10 个百分点，
就把默认引擎换成 LLM——但降级路径必须永久保留，那是无人值守的底线。

## ADR-002 引用闸门：裁掉句子，而不是标黄

**背景。** "结论有据"最容易做成一件装饰：给每句话加个来源标注，读的人还是分不清
哪些是有据的、哪些是模型补的。

**决定。** `synthesizer.verify()` 把答复按行拆开，事实句若没有引用**存在的** `ev:id` 就直接删除；
引用不存在的 id 则剔除引用；句中出现的数字若在被引证据里找不到等价写法，标记 `numeric_suspects`
并把任务降级为 `partial`。规则模式天生每行都带引用，所以它是"引用率 100%"的基线；
LLM 模式同一条闸门，没有豁免。

**为什么是删除而不是标注。** 巡检结论会被值班的人照着做。一句没依据但看起来很专业的
"预计 3 天后写满"，比少一句结论危险得多。删掉后附一句"已裁掉 N 条无证据表述"，
信息量其实更高。

**代价。** 会误伤：第一版把 `步骤 3：` 的序号也当数字查，导致正常答复变 `partial`；
`阻塞与未覆盖` 小节天生无证据可引，被删成空标题——**掩盖失败比丢失措辞严重**，
所以现在按小节粒度豁免。这两条都留下了对应测试。

**什么时候推翻。** 如果真实接入的生产结论里裁撤率长期 >15%，说明证据粒度太粗
（一条证据只支撑一句话），应该把 `harvest()` 拆得更细而不是放松闸门。

## ADR-003 不给 Agent shell，只给声明式工具

**背景。** 让 Agent "有用"最短的路是给它一个 `run_command`。最短的翻车路也是它。

**决定。** 运行时不提供任何 shell/subprocess 能力。所有能力都是显式声明的函数，
参数有类型与取值域，写操作 `side_effect=True` 默认必须逐名授权
（`--approve report_render`），未授权记为 `blocked` 挂起而不是报错。
`http_probe` 额外加了目标白名单（回环地址 + 巡检清单内的主机/IP）以堵 SSRF。

**代价。** 覆盖面受限于我预置的 14 个工具；真实运维里"就想顺手看一眼配置文件"这类需求做不到。

**说明一处细节。** 参数消毒里的 shell 元字符检查刻意**允许单个 `|`**：
`log_search` 的 pattern 是正则，`restart|OOM` 必须能过；拦的是 `&&`、`||`、`;`、
反引号、`$()` 这类串联。第一版按字符集一刀切，把诊断场景里最重要的那条日志查询毙掉了。

## ADR-004 轨迹用流式 JSONL，不用单个 JSON 文档

**背景。** Agent 是长跑任务，可能被打断；轨迹既要给人读，也要被评测和面板消费。

**决定。** `opspilot.trace.v1`：一行 header、N 行 event、一行 summary，
**每个事件产生时立即 flush**。`read_trace()` 校验 seq 连续，缺行报错。
脱敏（Key/口令）在落盘前完成，`mask_obj` 递归处理嵌套结构。

**代价。** 单个文件不是一个可直接 `json.load` 的对象，读侧要写 40 行解析；
并发写多条轨迹时文件数增长快（当前不做清理，属于已知待办）。

## ADR-005 合成数据 + 阴性对照主机

**背景。** 拿真实生产数据开源既不合规也不安全；但纯手写样例数据会让评测变得没有意义——
"样例里就一个故障，Agent 当然找得到"。

**决定。** `scripts/seed_demo.py` 用固定种子生成 8 台主机 × 72 小时指标 + 893 行日志，
**显式注入 5 类故障**（磁盘单调上涨 / OOM+连接池 / CPU 饱和 / 队列堆积 / 配置 P1），
并保留一台全程健康的 `cache-01` 作为**阴性对照**：Agent 不许在它身上无中生有。
数据文件与每份报告落款都写明"合成演示数据，非真实生产数据"。

**代价。** 指标分布是人造的，检测阈值在真实环境要重标；阴性对照只有一台，
"误报率"这个指标目前只能给下界，不能给置信区间。

## ADR-006 反思只补只读步骤，且按参数签名去重

**背景。** 第一版的去重按工具名，导致"关键词太窄查不到日志"时，反思器拒绝用更宽的
正则再查一次——而自我纠正恰恰是我要演示的能力。

**决定。** 去重粒度改为 `tool + args 的 JSON 签名`；`GAP_TOOLS["log"]` 给了两级放宽
（通用错误模式 → 只按 FATAL 捞）。反思阶段绝不引入写操作，补步轮数受 `MAX_REPLANS` 约束。

**代价。** 放宽关键词会带来噪声命中（例如把与告警无关的错误也算进来），
所以答复里必须把"检索用了哪个模式"写出来，让人能判断证据是否切题。
