# 已知局限

写这份文件的动机：面试官最想看的是候选人知不知道自己没做什么。以下是**当前真实边界**，
不是"未来展望"（展望在 README 的路线图上）。

## 数据与结论强度

- **数据是合成演示数据。** `scripts/seed_demo.py`，固定种子 `20261017`，8 台主机 × 72 小时。
  所有指标分布、日志措辞、历史故障均为人工设定，不代表任何真实生产环境。
  异常阈值（CPU 80 / 内存 85 / 磁盘 85）是拍的演示值，接真实环境必须重标。
- **阴性对照只有一台主机（`cache-01`）。** 因此"误报率"只能给出方向性结论，
  给不出置信区间。要主张准确率，需要几十台主机的标注集，本项目没有。
- **`root_cause_rank` 输出的 `probability` 是相对占比，不是校准概率。** 它由
  证据可靠度 × 规则强度归一化而来，能用来排序假设，**不能**理解成"有 26% 的实际可能性"。
  答复里目前写的是"概率"，接真实场景应改成"相对置信度"或做校准。
- **容量外推用的是最小二乘线性回归。** 只有单调趋势可外推（R² < 0.6 时工具会拒答），
  但它处理不了周期性写入（日志按天滚动造成的锯齿）、也处理不了配额突变。

## 检索

- **BM25 用中文 bigram 分词，没有语义检索。** 好处是零依赖、可预测；代价是同义表述
  （"磁盘快满了" vs "存储水位告警"）召回会下降。没有做 embedding 检索是有意的：
  演示项目里引入向量库只会增加"看起来复杂"，不会增加可解释性。
- **手册内容是我按运维经验写的 8 篇，不是从任何公司知识库里导出的。**

## LLM 路径

- **CI 与评测默认跑在规则引擎上。** 没有 API Key 时，`PLAN_MODE=auto` 直接走规则，
  LLM 分支的代码路径（`planner.llm_plan` / `synthesizer.llm_answer`）在 CI 里**只被单测
  以 mock 覆盖，没有被真实模型跑通过**。README 不会声称"LLM 规划已验证提升 X%"。
- **未做 token 预算与上下文压缩的精细控制。** `EvidenceLedger.to_prompt()` 有一个
  3000 字符的粗截断（按可靠度从低到高丢证据），真实长会话需要更细的策略。

## 工程边界

- **单进程、单机、无并发任务队列。** `OpsPilotAgent.run()` 是同步的；`app/server.py`
  的 `/api/run` 会阻塞该请求直到跑完，没做任务化/排队/取消。
- **单步超时只做到"不再等"，没做到"真的杀掉"。** `_invoke_with_timeout` 用
  `ThreadPoolExecutor` + `shutdown(wait=False, cancel_futures=True)`：超时后本步立即放弃推进，
  但 Python 线程无法强杀，跑飞的工具线程仍会留在进程里自然结束。生产做法应是子进程 + 硬超时。
  （第一版这里写的是 `with ThreadPoolExecutor(...)`，退出时 `shutdown(wait=True)`
  会把"超时"变成只约束返回值、不约束墙钟——被一条 `xfail` 钉出后已修复。）

## 本轮修掉的缺陷（保留记录，不抹历史）

测试与评测抓出 6 个真实缺陷，全部已修并有回归用例：未知主机名导致规划器 `KeyError`；
无证据时的拒答句被自己的引用闸门删成空标题；超时不约束墙钟；参数消毒与声明清单两套事实来源；
`notify_send` 在未实现投递的情况下声称"已投递"；`report_render` 对未知主机返回成功并落一份空报告。

保留这段的意义：一个声称没有 bug 的作品集，通常意味着没人真的跑过它。
- **工具完全不落地 shell，是本项目的架构前提，不是运行时防护。** 也就是说：
  如果有人新增一个会执行命令的工具，护栏并不会自动拦住它——护栏拦的是参数污染与越权写，
  不提供沙箱。
- **`write_trace` 无保留策略。** 每次运行一个 JSONL 文件，长期跑会累积（清理是路线图项）。
- **工单/通知台账是本地 JSONL**，没有接任何工单系统或 IM；`notify_send` 默认 dry-run，
  真实投递路径未实现（不是禁用，是没写）。
- **面板没有鉴权。** 它按"本机/内网只读观测工具"设计，`/api/run` 会真的执行任务，
  所以**不要把它暴露到公网**。若要对外，必须加身份认证与写授权的服务端校验。

## 评测

- **评测断言的是"工具序列 / 证据覆盖 / 引用完整性 / 护栏命中 / 该不该报这个故障"，
  不是"答案写得好不好"。** 文风质量没有评（那需要人评或模型评，会引入不可复现因素）。
- **幻觉拦截能力是通过"注入无证据句子，看 verify() 是否删除"来验证的**，
  这验证的是闸门的机制，不等于"本系统在生产环境中不会产生幻觉答复"。
- **规则模式与 LLM 模式的对比需要 API Key 才能跑**；无 Key 时评测报告里会显式写
  "LLM 组：已跳过"，而不是留一个空白让人误以为已经对比过。

## 我们故意不做的

- 自动发布、自动执行修复命令、自动发通知（默认 dry-run）——写操作一律要求人工授权；
- 多 Agent 辩论 / Agent 间通信协议：本项目的复杂度预算花在"证据可追溯与可评测"上；
- 向量数据库、LangChain 等框架依赖：核心运行时保持 stdlib-only。
